# アーキテクチャ

## 構成

| 部分 | 技術 | 役割 |
|---|---|---|
| 問題生成 | Python（Mortal・libriichi） | 自己対局から問題データを作る。公開前に一度だけ実行する |
| Web API | Cloudflare Workers、D1 | 出題・採点・ランキング（`web/worker`） |
| Webクライアント | TypeScript（フレームワークなし）、Vite | 画面・演出・共有画像（`web/client`）。問題画像と共有画像はCanvas、印はSVG、音はWeb Audioの合成で作り、画像・音声ファイルを配信しない |

- WebはMortalを実行しない。採点に使うQ値は問題データとしてD1に持つ。
- APIはWorkers無料プランのCPU上限（1リクエスト10ms）に収める。サーバーで画像を生成しない。
- 配信はGitHub Actionsの手動ワークフロー（Deploy）で行い、D1のマイグレーションを当ててからWorkerを配信する。問題データの投入は公開前に一度だけ行う。

## 問題生成パイプライン

| 段 | 処理 | 出力 |
|---|---|---|
| selfplay | libriichiの対局エンジンで自己対局する | mjaiログ（`.json.gz`） |
| evaluate | ログを席ごとにlibriichiの`PlayerState`で再生し、行動可能な全時点の特徴量をまとめて推論する | 判断点ごとのQ値 |
| extract | [プロダクト仕様](プロダクト仕様.md)の対象・難易度・抽出・番号付けの規則を適用する | 問題JSONL |
| load | D1投入SQLを作る | — |

- libriichiのアリーナは同じseedを4回転（席替え）で打つため、同一モデル同士では4局とも同じ対局になる。1seedにつき1対局だけを生成する。
- アリーナのログには実行された行動のQ値しか残らず、見送った鳴きが欠ける。Q値はevaluateで取り直し、ログに残るQ値（リーチ宣言後を含む）と一致することを照合する。
- リーチを選べる判断は、その局面にリーチ宣言を加えた状態も推論し、リーチ打牌の候補を作る。
- 生成物にはMortalのソースcommitと重みのSHA-256を記録する。

## データ（D1）

| テーブル | 主な列 |
|---|---|
| problems | 番号、種別、難易度、局面データ、評価データ（候補とQ値・最善手）、生成元（seed・局・本場・席・イベント位置）、難易度内・種類内の通し番号（テーマ別問題集用）、回答数、得点合計 |
| players | 内部ID、公開ID、トークンのハッシュ、名前、最後に割り当てた問題（未回答なら他の問題を開かせない） |
| answers | プレイヤー、問題、選んだ行動、得点、ピタリ、回答日時（主キーはプレイヤー×問題） |
| player_stats | プレイヤー、期間（全期間または日本時間の日付）、回答数、得点合計、ピタリ数、ランキング対象か、平均点、ピタリ率 |

- 局面データは回答者の席から見える情報だけを持ち、回答前に返してよい。評価データは回答後にだけ返す。
- 回答時に`answers`・`player_stats`・`problems`の集計列を同じバッチで更新する。問題集の進み具合は書き込まず、表示のときに回答から数える（読み取り枠は書き込み枠の50倍あるため）。
- 回答1件の書き込みは索引を含め8～12行（回答2、期間別の集計2×2～4、問題の集計1、次の割当1）。D1無料枠（1日10万行）では1日約8,000～12,000回答が上限になる。
- ランキングは`player_stats`の索引から上位を読み、短時間キャッシュする。D1は読んだ行数で課金・制限されるため、`answers`の全件走査で集計しない。

## プレイヤー識別

- プレイヤー発行時にランダムなトークンを返し、D1にはハッシュだけを保存する。APIはトークンで本人を識別する。
- 書き込みAPIにレート制限を掛ける。
